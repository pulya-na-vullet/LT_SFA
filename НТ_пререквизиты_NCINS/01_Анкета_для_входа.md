# Анкета для входа — NCINS в SFA

**Модуль:** некредитное страхование ЮЛ в SFA / ЕОС.ЮЛ (`ufr-eos-ul-ncins`)  
**UI:** «Страховки для бизнеса» / операция «Цифровое Страхование»  
**Версия:** 0.2  
**Дата:** 16.09.2026

Не путать с NSSFA («Нефинансовые сервисы ЮЛ») и с UMP-воркерами: UMP — соседний контур того же продукта.
Эта анкета — постановка **на модуль SFA целиком**. Паспорт подов — приложение Д, заглушки — А,
стенд — Б, нагрузка — Г, Jira — В.

> Раздел 2 (полная информация) и подробные REQUEST/RESPONSE по REST SFA заполняются после
> заключения инженера НТ и доступа к коду/Swagger. Сейчас закрыто то, что есть в helm/config и в UMP-доках.

## 1. Минимальная информация для определения необходимости НТ

Форма как в UMP. Значения без источника не подставлялись.

| № | Пререквизит | Значение | Где взять | Роль |
|---|---|---|---|---|
| 1 | Описание алгоритма тестируемого метода | Модуль SFA оформляет полис некредитного страхования ЮЛ и оркестрирует соседний процесс UMP `ump-ncins-pa`. Известный сквозной контур — раздел «Стык с UMP». Пошаговый алгоритм экранов и REST `core-api` — `_TBD_` (git NCINS + Confluence) | core-api/UI, Swagger, БП | Разработчик |
| 2 | SLA по времени отклика | `_TBD_`. **Не копировать 30 сек** с `ump-prepare-documents-ncins-pa` (это BPMN, не HTTP SFA). Ориентир ЕОС.ЮЛ по другим модулям — 2–10 сек на шаг UI; для NCINS взять из ТЗ | ТЗ / аналитик | Аналитик |
| 3 | ЧПН | **≈89 заявок/час** среднее, **≈180/час** пик. База СА 15 000 заявок/мес SFA (UMP). Это ЧПН **заявок**, не методов API | приложение Г | Аналитик |
| 4 | ЧПН через полгода | `_TBD_` (в UMP тоже TBD) | аналитик | Аналитик |
| 5 | ЧПН на вызываемые внутри методы | Для операций «один раз на заявку» верхняя оценка = п.3. Фактические вызовы accounts/customers/sign меньше из-за Redis TTL 60 мин. Точные цифры по Feign/Kafka — `_TBD_`. Из UMP: create-contract / payment ≈85–170/час; EA на стороне UMP ×3 | UMP-доки + код SFA | Аналитик |
| 6 | ЧПН через полгода на внутренние вызовы | `_TBD_` | аналитик | Аналитик |

Открытое расхождение UMP: `ump-main-ma-ncins-pa` даёт **250/час**. В анкету не подмешивать, пока аналитик не выберет одну базу (приложение Г).

По критериям шаблона поток заявок ≫ 1/час в пике → **основание завести задачу на НТ**. Решение — у команды НТ (приложение В).

Пока нет OpenAPI, профиль строится вокруг **бизнес-событий**, а не вокруг выдуманного числа HTTP на заявку.

|---|---|---|---|---|---|
| UC01 | Карточка модуля / вход в «Цифровое Страхование» | `_TBD_` | `_TBD_` | `_TBD_` | Нагрузка СП, не 1:1 с заявками |
| UC02 | Загрузка UI | `_TBD_` | `_TBD_` | `_TBD_` | Статику не складывать с API |
| UC03 | Клиент и счета (через core-api) | `_TBD_` ≤ потока заявок | `_TBD_` | `_TBD_` | Кэш 60 мин; фильтр RUR/CA/100 |

### UC04 — создание заявки в UMP

Authorization: Bearer <token realm ump>

### UC05 / UC06 — Kafka подписание и оплата

Направление SFA → UMP в конфиге: топик `TO_UMP_PROC_FROM_SYS_TEST`
(`spring.kafka.producer.topics.to-ump-proc-from-sys`).

`correlationKey` = `applicationId + "." + "NON_CREDIT_INSURANCE"`.

**Подписание, вернуть управление** (`messageName` всегда `SigningDocs`):

```json
{
  "messageName": "SigningDocs",
  "correlationKey": "1d462eee-1acf-406c-b07d-b4a3607f9741.NON_CREDIT_INSURANCE",
  "variables": {
    "agreementLink": "90542eee-1acf-406c-b07d-cca3607f958a",
    "id": "1d462eee-1acf-406c-b07d-b4a3607f9741"
  }
}
```

**Оплата:**

```json
{
  "messageName": "paymentFinished",
  "correlationKey": "1d462eee-1acf-406c-b07d-b4a3607f9741.NON_CREDIT_INSURANCE"
}
```

Header `systemCode` в `ump-main` описан как **всегда NIB**. Для канала SFA это конфликт с остальными
воркерами — `_TBD_`.

UMP → SFA (принять подписание), топик `ump.process.to.system`:

```json
{
  "applicationId": "c6e96f1d-60eb-4a61-8846-2061e6060353",
  "correlationKey": "c6e96f1d-60eb-4a61-8846-2061e6060353.NON_CREDIT_INSURANCE",
  "messageName": "SigningDocs",
  "variables": { "inn": "1231234234", "programId": 1 }
}
```

Как SFA принимает это сообщение (consumer) — в config producer описан, consumer **не виден**. `_TBD_` по коду.

### UC07 — создание договора `POST /v1/ins-contracts`

В UMP-комплекте **два разных адреса**. Нельзя выбрать молча.

**Вариант A** (`ump-main-ma-ncins-pa`) — вызов **в SFA**:

```http
POST https://int.ufrulkint-api.moscow.alfaintra.net/ufr-eos-ul-ncins-core-api/v1/ins-contracts
```

На ЛТ хост заменить на `lt.ufrulklt-api.moscow.alfaintra.net` + путь через gateway:

`/ufr-eos-ul-ncins-gateway-router-api/ufr-eos-ul-ncins-core-api/v1/ins-contracts`  
(сессия gateway для `/core-api/**` обязательна, если вызов идёт как пользовательский;
вызов UMP→SFA может идти иначе — `_TBD_`).

```json
{
  "programId": 1489,
  "signDate": "2026-08-02T21:08:36.218Z",
  "beginDate": "2026-08-02T21:08:36.218Z",
  "endDate": "2026-08-02T21:08:36.218Z",
  "duration": 1,
  "paymentType": "payment_account",
  "contractNumber": "string",
  "debitAccount": "string",
  "insuranceSum": 0.1,
  "insurancePremium": 0.1,
  "sellerId": "string",
  "sellerChannel": "SFA",
  "contractLink": "string",
  "policyLink": "string",
  "agreementLink": "string",
  "owner": {
    "ownerId": "string",
    "inn": "string",
    "ogrn": "string",
    "phoneNumber": "string",
    "email": "user@example.com",
    "legalAddress": "string"
  },
  "insuranceObjects": [
    {
      "employeeFIO": "string",
      "employeeEmail": "user@example.com",
      "employeePhoneNumber": "string",
      "employeeBirthDate": "2026-08-02",
      "paymentAccount": "string",
      "cadastralNumber": "string",
      "area": 0.1,
      "realEstateAddress": "string",
      "realEstateType": "COMMERCIAL"
    }
  ]
}
```

Ответ в `ump-main`: `200 {"OK"}`.

**Вариант B** (`ump-finalisation-ncins-pa`) — UMP сам бьёт в **NIB**, не в SFA:

```http
POST https://corp-gateway-test.moscow.alfaintra.net/corp-ncins-acc-gateway/secure/corp-ncins-acc-corp-ncins-acc-api/v1/ins-contracts
A-channelId: ump
A-projectId: ncins
A-clientType: BACKEND
```

Ответ в том доке: `201 Created` + Camunda `{ "result": "SUCCESS" }`.

У SFA при этом всё равно есть Feign `nib-api` на тот же NIB. Возможны оба плеча (SFA как фасад и/или UMP напрямую). Для скриптов НТ зафиксировать один боевой путь.

### Черновик сквозного сценария (для согласования)

1. Сессия ЮЛ, уровень ≥ 1, роль `NCINS_UL_ACCESS`.
2. Карточка модуля → UI.
3. Клиент и счета (только RUR/CA/100).
4. Создание заявки в UMP (`NON_CREDIT_INSURANCE`) — параметризация п. UC04.
5. Дождаться передачи на подписание; вернуть `SigningDocs` в `TO_UMP_PROC_FROM_SYS_TEST`.
6. Вернуть `paymentFinished`.
7. Create-contract по выбранному варианту A или B.
8. Не включать access-checker в профиль.
9. Error-ветки и OBIP — отдельные UC после появления API.

## Стык с UMP (обязателен в постановке)

```text
SFA UI/API
  → POST UMP /applications          старт ump-main-ma-ncins-pa
UMP prepare-documents / payment / signing / finalisation / delete-documents
  ⇄ Kafka SigningDocs, paymentFinished
  → POST SFA /v1/ins-contracts      (если верен вариант A)
  → POST NIB /v1/ins-contracts      (если верен вариант B)
```

Пререквизиты шести UMP-воркеров уже есть. Анкета SFA не должна им противоречить:
та же база 15 000/мес, тот же productCode `NON_CREDIT_INSURANCE`, те же correlationKey
и маска договора — пока аналитик не скажет иначе.
